 4. 新发现的阻塞性缺陷: StackStream poll 忙等空转
==================================================================
现象
  单进程内连续 dial 若干次后, 某一个连接永久卡住, 该进程 CPU 打满约 190% (近 2 核),
  且永不恢复。nativecheck 场景 (每次新进程) 完全看不到该问题。

现场证据 (卡死进程 /proc 采样)
  CPU        : 187% / 193% (3 秒采样两次)
  线程状态   : 2-4 个 task 处于 R 态; 主线程 State=S (sleeping)
  wchan      : 其余线程 futex_wait_queue_me, 但有 2-4 个在跑 -> 不是全挂 futex 死锁
  最后一次请求: read_timeout 20088 / 20101 ms (20s IO 超时)
  RSS/fd/socks: 卡死后完全静止不涨 -> 纯 CPU 自旋, 不是泄漏
  SAMPLE 计数 : 永久定格 (如 running 61 之后再无输出)

根因 (stack.rs 代码分析)
  poll_read / poll_write 在以下 4 个分支都执行:
      cx.waker().wake_by_ref();
      return Poll::Pending;
    - try_lock 失败
    - !sock.can_recv() / !sock.can_send()
    - recv_slice / send_slice 返回 Err
  wake_by_ref() 是立即自我唤醒, 配合 2 ms pump 就成了不 sleep 的忙循环。
  当 socket 进入既非 Closed 也无数据可读的终态 (对端 RST 后), 多个 task 一起空转,
  永远不会再进入 Pending 等待, 于是永久占满 2 核。

  Drop for StackStream 若 try_lock 失败就静默放弃 set.remove(handle);
  注释称 socket 会在下次 sweep 被复用, 但代码里并不存在任何 sweep。
  这解释了 socks 偶尔为 1 (撞锁的 socket 永久残留), 但因不累积, 不构成泄漏。

 5. 明确结论
==================================================================
  A. 稳定性 (单请求视角): 893/893 = 100%, 30 分钟完全平坦, 无衰减、无失败聚集。
     p50 306ms / p90 1251ms / max 5463ms, 无一次触及 20s dial 超时。
     但每次 nativecheck 都是新进程, 掩盖了进程内长期运行的问题。

  B. 内存: 无泄漏。600 连接后 RSS 仅 +1244KB (2.1 KB/连接, 且递减),
     SocketSet 条目回到 0。

  C. fd: 无泄漏。nativepress fd 恒为 11, 36 轮 x 100 dials 无一例外。

  D. fix #4 (ABBA 死锁): 未复现。893 + 3500 次 dial 中无一次 futex 全挂形态。

  E. fix #5 (socket 泄漏): 已验证修复。socks 计数不随连接数增长。

  F. 新缺陷 (阻塞): StackStream poll 忙等, 单进程内会永久卡死并打满 2 核。
     hang_rate 14 轮中 5 轮卡死 (35.7%), lane2 36 轮中 2 轮 (5.6%),
     合计 50 轮中 7 轮 (14%)。
     趋势上随运行时间变差 (最后 3 轮连续卡死, 且分别只完成 170/101/25 次)。
     => 原生数据面目前不能用于长期运行的进程。

 6. 建议修复
==================================================================
  1) poll_read / poll_write 禁止无条件的 wake_by_ref 自唤醒。
     改为: 把 waker 存入共享注册表 (StackShared.wakers), 由 pump_once 在
     iface.poll() 之后统一 wake_all(); 只有真正拿到数据/腾出空间时才自唤醒。
  2) Drop for StackStream 不要依赖 try_lock 成功。
     改为: Drop 只把 handle 推入 pending_removal 队列 (独立短锁),
     由 pump_once 在持锁时 drain 并 remove。
  本机 708 行版 stack.rs 已包含这两个修复的原型 (StackShared + pending_removal),
  本次测试用的是服务器上的 646 行版, 尚未含该修复。
